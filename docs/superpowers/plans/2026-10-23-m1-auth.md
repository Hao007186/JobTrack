# M1 帳號系統 + 示範帳號 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal：** 實作註冊、登入（含失敗鎖定）、refresh 輪換、登出、`GET /me`、示範帳號與唯讀權限，並更新文件反映「取消 Email 驗證」的決策。

**Architecture：** 新增 `app/modules/users` 與 `app/modules/auth` 兩個模組。`auth/security.py` 是不碰 DB 的純函式（Argon2、JWT、refresh token 雜湊）；`auth/service.py` 處理業務規則並丟出自訂例外；`auth/router.py` 把例外轉成 HTTP 狀態碼並處理 cookie。access token 放 `Authorization: Bearer`，refresh token 放 HttpOnly cookie、DB 只存 SHA-256 雜湊。

**Tech Stack：** 既有的 FastAPI、SQLAlchemy 2.0 async、Alembic、pytest；新增 `pwdlib[argon2]`、`PyJWT`、`email-validator`。

**Spec：** [docs/superpowers/specs/2026-10-23-m1-auth-design.md](../specs/2026-10-23-m1-auth-design.md)

## Global Constraints
- 不做 Email 驗證、不寄任何信；不建 `email_verifications`、`notification_settings`
- 對外一律用 `users.public_id`（UUID），不露出流水號 id
- email 寫入與查詢前一律 `strip().lower()`
- 密碼 8～128 字元；`display_name` 選填、最多 50 字元
- access token：HS256，claims `sub`（public_id 字串）、`iat`、`exp`，有效 `ACCESS_TOKEN_MINUTES`（預設 15）
- refresh token：`secrets.token_urlsafe(32)`，有效 `REFRESH_TOKEN_DAYS`（預設 7），DB 存 SHA-256 hex
- Cookie：名稱 `refresh_token`、`HttpOnly`、`SameSite=Strict`、`Secure` 依 `COOKIE_SECURE`（預設 true）、`Path=/api/v1/auth`、`Max-Age` = refresh 有效秒數
- 連續失敗 **5** 次鎖 **15 分鐘**；示範帳號 email `demo@farewatch.local`
- 錯誤訊息（`detail`）照抄：「此 Email 已註冊」（409）、「Email 或密碼錯誤」（401）、「登入失敗次數過多，請稍後再試」（423）、「示範帳號尚未建立」（503）、「示範帳號為唯讀」（403）、refresh 失敗「請重新登入」（401）、access token 無效「未登入或登入已過期」（401）
- 時間欄位一律 `timestamptz`，程式內用 `datetime.now(UTC)`
- 指令在 `backend/` 下執行，除非另外註明；ruff、mypy strict 必須通過
- Commit 用 Conventional Commits、繁體中文，結尾加 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`
- 平台相關改動（loop、路徑）push 前在 Linux 容器 `python:3.14-slim` 跑一次 pytest

## Review Focus
1. **refresh 偵測到重用時，作廢必須真的寫進 DB**：service 在丟例外前要先 `commit`，否則 router 回 401 時 session 被丟棄、作廢沒生效 → Task 4 測試在重用後用「另一張原本有效的 token」refresh 必須 401
2. **清除 cookie 的屬性要和設定時一致**：`delete_cookie` 沒帶相同 `path` 時瀏覽器不會刪 → Task 4 斷言 401 回應的 `set-cookie` 含 `Path=/api/v1/auth` 和 `Max-Age=0`
3. **同時註冊同一個 email**：先查再插入有競態，第二筆會撞 unique constraint 變 500 → Task 3 service 捕捉 `IntegrityError` 轉 409，測試用大小寫不同的 email 直接走到 DB 約束
4. **鎖定期間失敗次數不該繼續累加、鎖定到期後要能正常計數**：鎖定中回 423 且不改 `failed_login_count`；到期後再錯 1 次只算 1 次 → Task 3 測試
5. **竄改 JWT 的 `sub` 不是 UUID**（例如 `"abc"`）會在查 DB 時拋例外變 500 → Task 3 `get_current_user` 把無法解析的 `sub` 當成 401，加測試

`login` 的判斷順序：
1. 找不到使用者 → `verify_dummy_password`，丟 `InvalidCredentials`
2. `locked_until` 晚於現在 → 丟 `AccountLocked`（不動計數）
3. 密碼錯 → `failed_login_count += 1`；達 `MAX_FAILED_LOGINS` 時設 `locked_until = now + LOCKOUT_DURATION` 並把計數歸零；`commit` 後丟 `InvalidCredentials`
4. `is_active` 為 false 或 `is_demo` 為 true → 丟 `InvalidCredentials`
5. 成功 → 計數歸零、`locked_until = None`，`issue_tokens`

`register`：先查 email，存在就丟 `EmailAlreadyRegistered`；`commit` 時捕捉 `IntegrityError` → `rollback` 後丟 `EmailAlreadyRegistered`。
router 把 `EmailAlreadyRegistered` → 409、`InvalidCredentials` → 401、`AccountLocked` → 423。
`get_current_user`：解 token → `UUID(sub)`（`ValueError` 也視為無效）→ 查使用者，不存在或停用都 401。
